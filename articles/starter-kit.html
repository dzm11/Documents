PROPOSAL Giving non-designers a design-system-shaped starting point

One package, and every prototype starts on-system.

Product managers now build working prototypes in AI tools. What comes out looks like the tool, not like our product. The fix isn't more review — it's changing what the tool starts from. This is a proposal for a single npm package, owned by the design system team, that carries our components, our tokens, our screen patterns and a starter prompt. Plus the safety net that checks the result, and how that checker gets smarter every week.

00 — The problem

Everyone can build now. Nothing looks like us.

A product manager has an idea on Monday and a clickable prototype by Tuesday. That's genuinely good. The problem is what the prototype is made of.

AI prototyping tools — Lovable, v0, Bolt and the rest — generate from their own defaults. Generic blue buttons, generic spacing, a sidebar nobody in our product has ever used. The result is a demo that reads as "some app", not as our platform. Then one of two things happens: engineering rebuilds it from scratch, or the design system team spends a week explaining why it's wrong.

Reviewing harder doesn't fix this. By the time anyone reviews, the prototype has already been built on the wrong foundation. The only leverage point is the very first prompt.

Same person, same idea, same tool. The only thing that changed is what the tool had in its hands when it started.

01 — The idea

Ship the starting point, not the rulebook.

Documentation asks people to read and remember. A package asks them to type one line. So we ship the design system as something an AI tool can install and immediately use.

@splash/starter-kit is one npm package with two halves. The first half is code: real components, real tokens — the same ones production uses. The second half is context: a starter prompt, a description of how our screens are normally built, and realistic sample data.

The second half is the part people underestimate. An AI tool with our components but no context will still arrange them into a screen we'd never ship. Telling it how we build screens matters as much as giving it the parts. 

npm i @splash/starter-kit
import { Button, Table, TopBar } from '@splash/starter-kit'
import '@splash/starter-kit/tokens.css'   // colors, spacing, type
import starterPrompt from '@splash/starter-kit/prompt'
import { campaigns } from '@splash/starter-kit/mock-data'
The one-line version

We stop hoping people follow the design system, and start handing them a project that already does.

02 — Anatomy

What's actually in the box.

Five things. Each one removes a specific way prototypes go wrong.

@splash/starter-kit v1.4.0 · maintained by design system
/components
The real components Buttons, tables, inputs, navigation — the production ones, not lookalikes. Nothing to restyle later.
/tokens.css
Colors, spacing, type Synced from Figma. If a brand color changes, it changes here — and everything built on the kit follows.
/prompt
The starter prompt The paragraph a PM pastes before their first request. Tells the tool which components exist, which patterns to follow, and what never to invent.
/screen-patterns
How our screens are built Global top bar, horizontal tabs, filter row, data table. Written down once, so the tool stops inventing a left sidebar.
/mock-data
Realistic sample data Campaigns, budgets, audiences with believable names and ranges. Prototypes stop being demoed with "Lorem ipsum · $123".

Here's roughly what the starter prompt says. It is boring on purpose:

# Paste this before your first request.

Build with @splash/starter-kit only. Import components from the
package — never write a button, input or table by hand, and never
add another UI library.

Use tokens for every color, spacing and text style. No raw hex.

Screen structure: global top bar, horizontal tabs below it, then
page content. This product never uses left sidebar navigation.

Use @splash/starter-kit/mock-data for sample content.

If something you need doesn't exist in the kit, say so instead of
inventing it.
The last line matters

"Say so instead of inventing it" turns silent drift into a visible gap. Those gaps are also the best backlog the design system team will ever get — they're real, unmet needs, reported for free.

03 — In practice

Four steps, about ten minutes.

Nothing here requires a designer in the room. That's the point.

1
Install the kit One command in the AI tool's project. Some tools accept a starter template instead — we publish one of those too. PM · 1 min
2
Paste the starter prompt Copied from the package README. It's the same text for everyone, and it updates when the kit updates. PM · 1 min
3
Describe the feature and iterate Normal prototyping. The difference is that every screen comes out of our components, with our spacing and our data. PM · the actual work
4
Run Design Check on a screenshot Catches whatever slipped through. Returns a report and a ready-made fix prompt to paste back into the tool. PM · 2 min
04 — Ownership

The design system team owns this. Not engineering.

The most common objection is "who maintains it?" — usually asked by people worried it lands on their sprint. It doesn't.

This package is design system work: it's a distribution of what the DS team already maintains. Tokens come from Figma through the existing sync. Components come from the existing library. The prompt and the screen patterns are written by the person who knows them best — the design system designer. Product engineers are consumers, never maintainers.

Owner
Design system designer
  • Publishes and versions the package
  • Writes the starter prompt and screen patterns
  • Syncs tokens from Figma
  • Reads the gaps prototypes report back
Consumer
PM / vibecoder
  • Installs the kit, pastes the prompt
  • Builds and iterates freely
  • Runs Design Check before sharing
  • Doesn't need to know the design system
Downstream
Product engineers
  • Receive prototypes already using real components
  • Reuse the same package if useful
  • No maintenance duty
  • No rebuild from zero

Whoever owns the starting point owns the outcome.The reason this sits with the design system team

05 — Leverage

What this buys us.

A package is not just a convenience. It's a control surface we don't currently have.

  • One place to change things. A token change, a new component, a corrected pattern — publish once, and every project on the kit picks it up on the next install.
  • Versioning instead of arguing. "Which design system version is this prototype on?" becomes a number, not a conversation.
  • Prototypes become a signal. What PMs build, and what they report missing, tells us what the design system actually needs next.
  • The prompt is a product. When we learn that tools keep making the same mistake, we fix it in one paragraph — for everyone, retroactively.
Cost to a PM
Two minutes of setup, then their normal workflow.
Cost to engineering
Zero. They consume; they don't maintain.
Cost to the DS team
Real, but it's packaging work we already do, aimed at a new audience.
06 — The safety net

Design Check: the part that already exists.

The kit sets the starting point. Design Check verifies the finishing point. It's a working prototype today, not a plan.

You upload a screenshot of your prototype. A vision model (claude-sonnet-5) compares it against the Splash design system rules — tokens synced straight from our Figma file, plus component guidelines and the screen patterns distilled from real product screenshots. It returns a conformance score, at most seven plain-language findings, red numbered markers placed on the screenshot itself, and a fixPrompt.

The fixPrompt is the trick. Findings are written for a human — "the button is bright red instead of the brand blue". The fix prompt is written for a machine, with exact variable names and raw values, so it works whether or not the receiving tool knows our tokens. The user doesn't read it. They paste it.

01Prototype built on the kit
→
02Screenshot uploaded to Design Check
→
03Score, findings on the image, fix prompt
→
04Fix prompt pasted back into the tool
re-check until the score stops moving

The loop usually runs two or three times. Each pass is a couple of minutes, and no designer is blocked on it.

Why the pair works

The kit prevents most drift. Design Check catches the rest and tells you how to fix it in the same tool you're already in. Neither one requires a review meeting.

07 — Compounding

A checker that gets better every week.

Right now Design Check is as good as its prompt. It doesn't have to stay that way. Two loops turn ordinary use into a slowly improving reviewer — one fast, one slow.

Fast · per report
Humans grade the findings

Every finding gets a thumbs up or down. A thumbs down asks for one line: why was this wrong? Nothing else changes about the workflow.

01Designer or PM marks a finding true / false
↓
02A false one collects a one-sentence reason
↓
03Reasons cluster into repeat mistakes
↓
04Rules and prompt updated — false alarms stop recurring
Slow · weekly batch
A stronger model grades the checker

Every audit is stored as a pair: the screen, and what Sonnet said about it. Once a week, a more capable model re-reviews the batch.

01Store every screenshot + audit in a database
↓
02Weekly, re-run the batch through Opus or Fable
↓
03Compare: what did the fast model miss or overcall?
↓
04Distil the difference back into the everyday auditor

The two loops answer different questions. Thumbs up and down tell us where the checker is annoying — the false positives that make people stop trusting it. The weekly batch tells us where the checker is blind — the real problems a stronger model catches and ours walks past.

Both produce the same kind of output: examples. Enough graded examples and you have a genuine evaluation set — the thing that lets you change the prompt and know whether you made it better instead of guessing. That set is also what you'd need later if we ever wanted to fine-tune a smaller, cheaper model to do the routine passes.

Order of operations

Do the cheap loop first. Thumbs up / down is a day of work and immediately tells us whether people trust the tool. The weekly batch only pays off once there's enough traffic to have a batch worth re-running.

One thing to decide early

Stored screenshots are product screens. Agree up front on where they live, who can read them, and how long they're kept — before the database exists, not after.

08 — Where to start

The smallest version worth shipping.

None of this needs to be complete to be useful. The first version can be embarrassingly small.

  • Week one: the starter prompt alone, published as a page. No package yet. See whether prototypes improve just from the paragraph.
  • Week two to four: the package with tokens, the ten most-used components, and mock data.
  • Then: screen patterns, and Design Check pointed at the same rules the kit ships.
  • Then: thumbs up / down on findings, and only later the weekly batch re-review.

The order matters more than the scope. Every step in it is useful on its own, and each one makes the next one cheaper.

The whole proposal, compressed
Give people a starting point that's already right.
Check the result automatically, and hand back the fix.
Let every check make the next one better.
